## Problem Statement

`backend/app/services/regime_builder.py::run_regime_batch(repo, start, end)` is the dashboard's **市场环境聚合** feature (daily batch compute of regime indicators). It is the **second most complex service-level function** in `app/services/` after Path A-4's `build_sector_rotation`, and the first **daily-grain multi-batch** target:

- 240+ lines split across `_compute_batch` (line 329, ~30 lines orchestration) + `_aggregate_daily` (line 150, ~170 lines heavy group_by + agg) + `_scan_enriched_fallback` (line 367, ~70 lines multi-batch loop) + cache helpers
- Heavy Polars expression usage (`compute_indicators` 70-column chain at line 365; `_aggregate_daily` 14-aggregation group_by at line 177-)
- Multi-batch state: `[start..end]` 分 N 个 batch (每批 ≤ `batch_days=60`天,带 `warmup_days=40` prefix) per `_scan_enriched_fallback` line 419-437
- IO sources: `kline_daily_enriched` (path glob: `enriched_dir / "**" / "*.parquet"` line 339) + `instruments_ext/instruments.json` (via `repo.get_instruments()` line 400) + `historical_shares.parquet` (via `repo.get_historical_shares()` line 401) + `kline_index_daily/000001.SH` change_pct (via `repo.get_index_daily(...)` line 446)

The single public function `run_regime_batch(repo, start, end)` is called by:
- Daily pipeline (`backend/pipelines/daily.py`)
- Manual regime_history refresh (`compute_regime_incremental` line 647, `detect_stale_dates` line 596)
- 15+ pytest tests at `backend/tests/test_regime_builder.py`

The Path A-4 service-level seam contract (ADR-0006 §"5 段" + Path A-4 amendments) is **proven** to work for single-shot orchestration with 8 kernels. Path A-5 is the first **multi-batch daily-grain** target — it refines ADR-0006's "5 段" with explicit guidance on per-batch dispatch + cross-batch `pl.concat` + `HashMap<String, f64>` kernel input.

## Solution

Migrate `_compute_batch` + `_aggregate_daily` to Rust kernels registered in the existing `tf_rs_indicators` cdylib as 2 separate `#[pyfunction]` entry points. The public `run_regime_batch(...)` and helper function names are **preserved** (no `_py_*` rename per Q4) — function bodies are modified to do `try-import tf_rs_indicators` and dispatch to Rust kernels when available, falling back to the original Python body otherwise. The 6-stage `_scan_enriched_fallback` multi-batch loop wraps the per-batch adapter dispatch.

Per the established Path A-3 + Path A-4 service-level seam contract (ADR-0006 §"5 段"):

1. **Pre-aggregate by Python adapter**: the heavy Polars block `compute_indicators` (70-column Polars expression chain) stays in Python per Q3=a — migrating Polars expression chain to Rust 1:1 is too verbose vs gain. The `_aggregate_daily` per-day group_by + agg IS migrated (single `group_by + agg` like Path A-4's `per_bucket_reduce_kernel`).
2. **Multi-arg kernel signatures**: 2 kernels each take 2-4 typed parameters; `compute_batch_kernel` is an IO helper kernel (takes `PathBuf` for enriched_dir per Path A-4 ADR-0006 §"5 段"§1+§3 amendment); `aggregate_daily_kernel` takes 2 `PyDataFrame` (per-stock rows + index_pct_map `HashMap<String, f64>`).
3. **Kernel pure-compute on `PyDataFrame` round-trip**: IO helper kernel consumes parquet internally via `polars::prelude::PlParquetReader::new(pathbuf).finish()?` (per ADR-0006 §"5 段"§1+§3 Path A-4 amendment — `polars` crate handles IO internally, kernel remains pure-compute on resulting DataFrame). Reduce kernel consumes 2 `PyDataFrame` round-trip (per Q7=a Path A-4 convention).
4. **Kernel returns `polars::DataFrame` via `PyDataFrame`**: outputs projected by the adapter via zero-copy round-trip; no `iter_rows(named=True)` translation overhead for 5M-cell daily data.
5. **Cache owned by caller**: `_scan_enriched_fallback` and `run_regime_batch` are NOT module-level cached (per Q9 — daily batch compute cache semantics = "已算过的 date 集合", owned by caller via `regime_history.parquet` + `detect_stale_dates` + `upsert_regime_history`). The adapter adds NO new `_cache` / `_cache_ts`.

### 2 Rust kernels registered in `tf_rs_indicators`

| # | Kernel | Input shape | Output shape | IO? |
|---|--------|-------------|--------------|-----|
| 1 | `compute_batch_kernel` | `PathBuf` (enriched_dir) + 3 scalar (`batch_start: &str`, `batch_end: &str`, `warmup_days: u32`) | `PyDataFrame` | **yes (parquet)** |
| 2 | `aggregate_daily_kernel` | 2 `PyDataFrame` (per_stock_df + index_pct_map `HashMap<String, f64>`) | `PyDataFrame` | no |

`mod.rs` exports these 2 sub-module functions + 2 `#[pyfunction]` bindings. `lib.rs` registers 2 new `wrap_pyfunction!` calls — total cdylib function count reaches **16** (1 hello-world `sum_close` + 3 Path A-3 + 2 Path A-1/2 + 8 Path A-4 + 2 Path A-5).

### Adapter orchestration order in `run_regime_batch`

The thin adapter orchestrates 2 kernel calls + Python glue in the following order:

1. **Param validation** (Python) — `start <= end`, `start`/`end` are `date` instances
2. **Index pct map** (Python) — `_load_index_pct(repo, start, end)` populates `{date: change_pct}` dict from `repo.get_index_daily(...)`
3. **Excluded symbols** (Python) — `load_risk_warning_symbols(...)` if `preferences.get_sentiment_exclude_st()` (ST stocks excluded from regime aggregation)
4. **Enriched range check** (Python) — `repo.get_enriched_range(start, end)`; on cache miss → `_scan_enriched_fallback(...)` (multi-batch loop)
5. **Multi-batch fallback loop** (`_scan_enriched_fallback` line 419-437, per-batch adapter dispatch):
   - Per batch: `df = _compute_batch_via_kernels(...)` (or `_py_compute_batch` on fallback) — kernel 1
   - Per batch: `df = _filter_excluded_symbols(df, excluded_symbols)` (Python, line 361)
   - Per batch: `daily = _aggregate_daily_via_kernels(df, index_pct_map)` (or `_py_aggregate_daily`) — kernel 2
   - Append `daily` to `daily_parts` list (Python)
6. **Cross-batch concat** (Python) — `pl.concat(daily_parts, how="vertical_relaxed")` (line 437); trivial PyO3 surface, kept in Python
7. **Upsert + return** (Python) — `upsert_regime_history(data_dir, new_rows)` line 549 + return DataFrame

The Python fallback (when `tf_rs_indicators` is unavailable) executes the same 7-step flow with all `*_via_kernels` calls replaced by the original `_py_*` aliases.

### Kernel signatures (per Q1+Q2+Q11)

#### `compute_batch_kernel(data_dir: PathBuf, batch_start: &str, batch_end: &str, warmup_days: u32) -> PyResult<PyDataFrame>`

Internally:
1. `warmup_start = batch_start - timedelta(days=warmup_days)`
2. `pl.scan_parquet(data_dir / "**" / "*.parquet").filter(date >= warmup_start AND date <= batch_end).collect()`
3. Apply `compute_indicators(df, needed={"change_pct", "ma20"})` Polars expression chain (Python pre-aggregate, per Q3=a)
4. If `instruments` not None + non-empty: apply `compute_limit_signals(df, instruments, needed={"signal_limit_up", "signal_limit_down", "signal_broken_limit_up"}, historical_shares=...)` (Python)
5. `with_prev_consecutive(df)` (Python — symbol shift via `pl.col().shift(1).over("symbol")`)
6. Filter `date >= batch_start AND date <= batch_end` (drop warmup rows)
7. Return resulting DataFrame (per-stock rows with indicator columns)

Empty case: `pl.DataFrame()` (no enriched parquet → empty).

**Note**: per Q8, this kernel is an IO helper — takes `PathBuf` and reads parquet internally via `PlParquetReader::new(pathbuf).finish()`. Per ADR-0006 §"5 段"§1+§3 Path A-4 amendment, this is allowed because `polars` crate handles IO internally; kernel remains pure-compute on resulting DataFrame.

#### `aggregate_daily_kernel(per_stock_df: PyDataFrame, index_pct_map: HashMap<String, f64>) -> PyResult<PyDataFrame>`

Internally mirrors `_aggregate_daily` line 177-` (Polars expression 14-aggregation group_by + agg):

1. Filter `needed` cols (per `_aggregate_daily` line 165-170: `date`, `change_pct`, `amount`, `signal_limit_up`, `signal_limit_down`, `signal_broken_limit_up`, `consecutive_limit_ups`, `close`, `ma20`)
2. If `consecutive_limit_ups` available + `symbol` column: `with_prev_consecutive` (in Rust via `pl.col().shift(1).over("symbol")`)
3. Single `group_by("date").agg(...)` with 14 aggregations:
   - `change_pct.gt(0).sum().alias("up_count")`
   - `change_pct.lt(0).sum().alias("down_count")`
   - `pl.len().alias("total_count")`
   - `change_pct.mean().alias("avg_pct")`
   - `change_pct.median().alias("median_pct")`
   - `change_pct.ge(0.03).sum().alias("strong_up_count")`
   - `change_pct.le(-0.03).sum().alias("strong_down_count")`
   - `signal_limit_up.cast(Boolean).sum().alias("limit_up")`
   - `signal_limit_down.cast(Boolean).sum().alias("limit_down")`
   - `signal_broken_limit_up.cast(Boolean).sum().alias("broken_limit")`
   - `consecutive_limit_ups.max().alias("max_consecutive")`
   - `amount.sum().alias("total_amount")`
   - `amount.mean().alias("avg_amount")`
   - MA20 above pct (per `_aggregate_daily` line 222-228): `_above_cnt` + `_above_total` → `_ma20_above_pct`
4. Join `index_pct_map` by date string → `index_pct` column (per line 240-244 of `_aggregate_daily` docstring; not in current `_aggregate_daily` body but referenced as expected output)
5. Return resulting DataFrame (per-day rows with 14 indicator columns + `index_pct`)

- [x] **T04 finding 5 — fast-route vs slow-route asymmetry** (found after the
      closure commit, 2026-10-20, while writing the live-API contract test):
      `run_regime_batch()` has two routes that can disagree.
      * FAST route — `repo.get_enriched_range()` hits the in-memory enriched
        history cache. When that cache was built by the full computation it
        carries the limit signals and the route is correct; when the enriched
        refresh **falls back to the raw 14-column parquet** it does NOT, and
        the route silently yields `limit_up=0`, `first_board=0`,
        `ge2_count=0`, `promo_rate=None` → the frontend's ladder cards would
        render 0 / "—".
      * SLOW route — `_scan_enriched_fallback()` → `_py_compute_batch()` →
        `compute_indicators` + `compute_limit_signals` → `_py_aggregate_daily`.
        Always correct.
      The **Rust kernel path always mirrors the SLOW route** (kernel 1 rescans
      the parquet; the Python pipeline always runs `compute_limit_signals`), so
      the kernel path is unconditionally correct. Pinned by
      `backend/tests/test_rs_regime_live_api_contract.py::test_kernel_route_is_never_degraded`.
      Related: `above_ma20_pct` is slightly sensitive to where the batch
      boundaries fall (the warmup prefix shifts the ma20 rolling window at a
      batch's first days) — any cross-implementation comparison must reproduce
      the **same batch partition**.

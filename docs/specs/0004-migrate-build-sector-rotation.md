# Spec 0004 — Migrate `services.sector_rotation.build_sector_rotation` (+ 5 helpers) to Rust kernels

> Generated by `mattpocock-skills:grill-with-docs` on 2026-10-19 (4 rounds, 16 decisions).
> Author: Path A-4 (first **multi-kernel** service-level migration; second service-level target after Path A-3).
> Status: **Ready-for-agent** (post-grill).
> Tracking: ADR-0006 (Path A-3 service-level seam contract) + this spec (Path A-4 pilot).
> Follows the established 5-ticket pattern: research → kernel → fixture → adapter+parity → closure.
> See [Spec 0003](0003-migrate-market-overview-dimension-rank.md) for the Path A-3 service-level pattern this spec extends.

## Problem Statement

`backend/app/services/sector_rotation.py::build_sector_rotation(repo, kind, ...)` is the dashboard's
**盘中板块切换走势** feature. It is the most complex Python function in the entire
`app/services/` tree:

- 240+ lines split across `_compute` (73 lines) + 4 IO helpers + `_rank_for_mode` (55 lines) + cache
  logic + param validation
- 4 IO sources (`kline_minute` parquet, repo concept map, ext flow parquet, daily close parquet)
- Heavy Polars expression usage (bucketize + group_by + agg at line 420-435; activity_map at
  line 540-551)
- Stateful loops with `prev_sign` dict for cross-event detection (line 446-475)
- Module-level cache (`_cache` + `_cache_ts` + TTL + LRU eviction)

Single API endpoint (`app/api/sector_rotation.py:43`) + 30+ pytest tests depend on it.
Empirically observed dashboard latency spike when this function runs concurrently with
`build_market_overview` (which Path A-3 already accelerated).

The Path A-3 service-level seam contract (ADR-0006) is **proven** to work for a single
pure-compute kernel + 2 helpers. Path A-4 is the first **multi-kernel + IO + cache** service-level
target — it will refine ADR-0006's "5 段" with the addition of **`PyDataFrame` round-trip as
acceptable pre-aggregate input** (kernels may consume `polars.DataFrame` Series indirectly via
the adapter's pre-aggregate step, even though the kernel itself does not read `Path` filesystem
handles directly).

## Solution

Migrate all 6 functions in `sector_rotation.py` to Rust kernels, registered in the existing
`tf_rs_indicators` cdylib as 8 separate `#[pyfunction]` entry points. The public
`build_sector_rotation(...)` and helper function names are **preserved** (no `_py_*` rename
per Q5=b) — function bodies are modified to do `try-import tf_rs_indicators` and dispatch to
Rust kernels when available, falling back to the original Python body otherwise. The
module-level cache (`_cache` / `_cache_ts` / TTL / LRU) is **kept inside the thin adapter**
(per Q4=b / Q10=a), not moved to the caller.

Per the established Path A-3 service-level seam contract (ADR-0006 §"5 段"):

1. **Pre-aggregate by Python adapter**: the heavy Polars block at `_compute` line 420-435
   (bucketize + group_by/agg) and line 540-551 (activity_map) stay in Python — these are
   the "Polars expressions" of the Path A-4 hot path and remain in the adapter per Q3=a.
2. **Multi-arg kernel signatures**: 8 kernels each take 2-6 typed parameters; no kernel
   takes a single `polars.DataFrame` because the inputs cross multiple IO sources and need
   different per-kernel transformations.
3. **Kernel pure-compute on `PyDataFrame`/list[dict] input**: IO helpers consume `PyDataFrame`
   round-trip (Q7=a) following the indicator-level Path A-1/2 pattern; reduce kernels consume
   `list[dict]` (per Q15=c) following the Path A-3 `_dimension_rank_kernel` pattern.
4. **Kernel returns `polars::DataFrame` via `PyDataFrame`**: outputs are projected to dict-of-list
   by the adapter via `df.iter_rows(named=True)`, matching the indicator-level round-trip.
5. **Cache owned by Python**: `_cache` / `_cache_ts` / TTL / LRU live in the `build_sector_rotation`
   thin adapter (Q4=b / Q10=a), keyed on the full argument tuple. Adapter checks cache before
   any kernel call; kernel + reduce functions are stateless.

## Implementation Decisions

### 8 Rust kernels registered in `tf_rs_indicators`

Per Q1=c (迁全部) + Q2=c (多 kernel 拆) + Q6=a (全 4 IO helper 迁) + Q8=a (sort 独立 kernel) +
Q11=a (统一 sub-directory). The 8 kernels split the original 6-Python-function surface
into a finer-grained Rust surface because each kernel has a different signature shape
(IO helper vs reduce vs sort) and would not be cleanly expressible as a single function.

| # | Kernel | Source (Python) | Input shape | Output shape | IO? |
|---|--------|-----------------|-------------|--------------|-----|
| 1 | `bare_kernel(col: &str) -> Series` | `_bare` | single `&str` column name | `pl.Series` of the column expression | no |
| 2 | `prev_daily_close_kernel(data_dir: Path, target_date: &str) -> DataFrame` | `_prev_daily_close` | filesystem `Path` + date string | `pl.DataFrame` (symbol, close) | **yes** (parquet) |
| 3 | `minute_pcts_kernel(data_dir: Path, target: &str) -> (DataFrame, str, bool)` | `_minute_pcts` | filesystem `Path` + minute partition | tuple of (`pcts: DataFrame`, `basis: str`, `has_amount: bool`) | **yes** (parquet) |
| 4 | `sector_flow_kernel(data_dir: Path, flow_field: &str) -> (DataFrame, bool)` | `_load_sector_flow` | filesystem `Path` + flow field | tuple of (`flow: DataFrame`, `flow_available: bool`) | **yes** (ext parquet) |
| 5 | `per_bucket_reduce_kernel(by_sector_df: PyDataFrame, market_df: PyDataFrame) -> DataFrame` | `_compute` phase (b) | 2 `PyDataFrame` (per_sector pcts + market avg per bucket) | `DataFrame` (bucket, names, pcts, top_set, leader, leader_pct, cross_up, cross_down) | no |
| 6 | `timeline_kernel(per_bucket: Vec<HashMap<String, Py<PyAny>>>) -> DataFrame` | `_compute` phase (c) timeline | `list[dict]` of per-bucket summaries | `DataFrame` (time, rotation, leader, leader_pct, market_pct, cross_up, cross_down) | no |
| 7 | `cross_events_kernel(per_bucket: Vec<HashMap<String, Py<PyAny>>>) -> DataFrame` | `_compute` phase (c) cross_events | same `list[dict]` | `DataFrame` (time, name, dir, pct) — dir is "up"/"down" | no |
| 8 | `rank_for_mode_kernel(sectors: Vec<HashMap<String, Py<PyAny>>>, activity_map: HashMap<String, f64>, has_amount: bool, flow_by_member: HashMap<String, f64>, flow_available: bool, sort_by: &str) -> Vec<String>` | `_rank_for_mode` | `list[dict]` + 4 scalar params | `list[str]` (sector names in rank order) | no |

Per Q15=c: kernels 2/3/4 use `PyDataFrame` round-trip (Path A-1/2 indicator-style); kernels
5/6/7/8 use `list[dict]` (Path A-3 service-level style). The cross-style seam is OK because
the adapter orchestrates them — IO helpers are explicitly separate from reduce kernels.

### Adapter orchestration order in `build_sector_rotation`

The thin adapter orchestrates the 8 kernel calls + 5 Polars sections in the following order
(matching the original Python function flow):

1. **Param validation** (Python) — `kind in ("concept", "industry")`, `sort_by in _SORT_MODES`,
   `bucket_minutes in _ALLOWED_BUCKETS`, `top = max(5, min(100, top))`, `series_names` dedup,
   `exclude_sectors` default-or-custom, `rows_limit = ...`
2. **Cache check** (Python) — `hit = _cache.get(cache_key); if hit and not expired: return hit`
3. **Empty / no-data short-circuits** (Python) — returns `{"status": "no_data"|"empty", ...}`
   *before* any kernel call (per ADR-0006 §"5 段"§1: adapter pre-aggregate).
4. **IO kernel calls** (4 in parallel-friendly order, but sequential is fine for now):
   - `bare_kernel("symbol")` — used to construct the member map
   - `prev_daily_close_kernel(data_dir, target_date)` — for pct reference
   - `minute_pcts_kernel(data_dir, target)` — primary input
   - `sector_flow_kernel(data_dir, flow_field)` — secondary input
5. **Polars pre-aggregate** (Python) — the two Polars-heavy blocks at `_compute` line 420-435
   (bucketize + group_by/agg) and line 540-551 (activity_map). Inputs: kernel outputs from step 4.
6. **Reduce kernel calls**:
   - `per_bucket_reduce_kernel(by_sector_df, market_df)` — produces per_bucket list
   - `timeline_kernel(per_bucket_list)` — produces timeline rows
   - `cross_events_kernel(per_bucket_list)` — produces cross_events list
7. **Sort kernel call**: `rank_for_mode_kernel(sectors, activity_map, ...)` — produces ranked
   name list
8. **Output assembly** (Python) — build 5 output sections (`timeline`, `cross_events`, `sectors`,
   `series`, `universe`) from kernel outputs + Python glue
9. **Cache write** (Python) — `_cache[cache_key] = result; _cache_ts[cache_key] = now`
10. **Return** — `{"status": "ok", "timeline": ..., "cross_events": ..., "sectors": [...],
    "series": {...}, "universe": [...], ...}`

The Python fallback (when `tf_rs_indicators` is unavailable) executes the same 10-step
flow with all `*_kernel` calls replaced by the original Python functions (now living as
private `_py_*` aliases inside `sector_rotation.py`).

### Cache strategy (per Q10=a)

- **Scope**: module-level (`_cache: dict`, `_cache_ts: dict`) inside `sector_rotation.py`
- **Key**: `(kind, flow_field or "", top, bucket_minutes, tuple(series_names or ()),
  exclude_effective, rows_limit, sort_by)` — tuple of 8 elements
- **TTL**: preserved from current implementation (`_CACHE_TTL` constant; default 60s)
- **Eviction**: LRU — `while len(_cache) > _CACHE_MAX_ENTRIES: pop oldest` (preserved from current)
- **Migration impact**: cache lives in the thin adapter (`build_sector_rotation`), so the
  8-kernel Rust call sequence is **skipped on cache hit** (no Rust call at all when the
  10-step orchestrator short-circuits at step 2)

### ADR-0006 amendment (per Q12=a)

ADR-0006 §"5 段"§1 currently states: "kernel 不直接读 filesystem". The Path A-4 IO helper
kernels (`prev_daily_close_kernel`, `minute_pcts_kernel`, `sector_flow_kernel`) read parquet
files from a `Path` parameter. This is **not** a violation of the original §1 (kernels take
`Path` but don't read it directly — they call `pl.read_parquet(path)` inside Rust, where
`Path` is a data structure, not a "filesystem handle" per the ADR-0006 glossary). However,
the spirit of §1 was "kernels are pure-compute, no IO". The amendment clarifies:

> ADR-0006 §"5 段"§1 (amended 2026-10-19): "kernel 不直接读 `Path::read()` filesystem handles;
> `polars::prelude::ParquetReader::read(Path)` is allowed because the `polars` crate handles all
> IO internally and the kernel remains pure-compute on the resulting `DataFrame`. The adapter
> is responsible for passing validated `Path` values."

This amendment is **in place** in `docs/adr/0006-service-level-rust-migration.md` as part of
Ticket 05 (docs closure), not as a new ADR.

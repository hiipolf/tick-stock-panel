## Problem Statement

`backend/app/indicators/levels.py::_support_resistance(df, bins=40)` is the **Volume-Profile / 筹码分布** algorithm that underpins every "支撑位 / 压力位" line on the price chart (see the `LEVEL_TYPES['sr']` consumer in `frontend/src/components/stock-table/StockDataTable.tsx` and the AI prompt context in `app/stock_analysis.py`). The user opens a chart, the function runs over up to 60 months of daily K-line data, and the chart re-renders.

Today, the implementation lives in a `for row in range(n)` Python loop in `levels.py` that builds a `numpy.ndarray` of size `bins × n` (an in-place `_chip_decay` 2D array) and finally reduces to a few "POC + 2 dense zones" dicts. Across A-share universe (~5,400 stocks × 240 trading days × 40 bins = 51M float64 ops per refresh), the current implementation is a latency spike that the user feels whenever they switch symbols or recompute levels. The algorithm is numerically trivial — single-pass decay + reduction — but the **Python interpreter loop is the wall**.

Path A (`crates/indicators` + `pyo3-polars 0.28.0`) is verified end-to-end on a hello-world `sum_close` (commit `3cc0053`). The seam works: `polars.DataFrame` round-trips through Rust via `PyDataFrame` with the existing vendored Polars 0.55.2 patches. The work for this spec is to replace the Python loop body of `_support_resistance` with a Rust kernel, while keeping the Python function signature stable so no caller changes.

## Solution

Move the **compute core** of `_support_resistance` (the chip-decay 2D-array update + per-bucket reduction) into `crates/indicators/src/levels.rs`. Keep the Python-side `_support_resistance` function as a thin adapter that:

1. Receives a `polars.DataFrame` (already in memory) and `bins: int`.
2. Forwards the call to `tf_rs_indicators.support_resistance(df, bins)` via `pyo3-polars` `PyDataFrame`.
3. Receives a `polars.DataFrame` of the same height with a new `chip_pct` column appended (per-row chip distribution). Then re-runs the existing Python POC / dense-zone reduction (which is small, on a 1-D array of `bins` floats) and returns the `list[dict]` the caller already expects.

Two seam test layers as per ADR-0002 §4: Rust unit tests in `crates/indicators/src/levels.rs` (algo correctness), Python pytest in `backend/tests/test_rs_levels_seam.py` (end-to-end parity against a frozen golden vector from a one-time Python reference run).

## User Stories

1. As a chart user, I want to switch between A-share symbols and see support / resistance levels render in under 50 ms, so that the chart feels instant.
2. As a chart user, I want the rendered support / resistance levels to be **bit-identical** to today's Python implementation, so that existing chart annotations, markLines, and AI prompts don't shift.
3. As the AI stock analysis module, I want `levels._support_resistance(df)` to keep returning `list[dict]` with the same `value/label/type/side/strength` keys, so that the AI prompt template doesn't need a code change.
4. As a chart user, I want the function to **degrade gracefully** to the pure-Python path on machines without the Rust wheel installed (no `cargo` / `maturin` / Linux-only deps), so that CI on Windows desktop builds still produce a chart.
5. As a regression tester, I want a `pytest -k levels_seam` suite that fails loudly if the Rust kernel drifts from the Python reference, so that algorithm drift is caught before it reaches the chart.
6. As a regression tester, I want a `cargo test -p tf-rs-indicators` Rust unit test for the kernel that runs without Python, so that the algo can be benchmarked in isolation.
7. As a performance engineer, I want a `--release` build of the kernel to bring a 240-day × 5,400-stock refresh from "noticeable spike" to "sub-second", so that the per-symbol chart load is no longer the dominant cost.
8. As a maintainer, I want the Python wrapper at `levels.py` to stay small (≤ 30 lines), so that the public-API contract is auditable at a glance.
9. As a Rust contributor, I want the kernel in its own `levels.rs` module with `mod levels;` and `#[pyfunction] pub fn support_resistance(...)` (not hidden inside `sum.rs`), so that future indicators slot in via `crates/indicators/src/<name>.rs` (per ADR-0001).
10. As a release engineer, I want the wheel to stay on `pyo3-polars = 0.28.0` and `polars = 0.55.2` (with the vendored patches), so that binary compatibility is the same as the hello-world wheel — one wheel matrix to manage.
11. As a desktop-side release engineer, I want the wheel to be `abi3-py310` (matching the existing hello-world wheel), so that the desktop Tauri build pipeline picks it up with zero extra config.
12. As a maintainer of the vendored Polars patches (TF-RS-1), I want the new `levels.rs` kernel to only depend on Polars expressions that are covered by the vendored crate patches — no PythonScan / Delta / Object variants at runtime — so that a future polars 0.55.3+ bump doesn't silently break levels.
13. As a future indicator author, I want the seam test scaffolding (`backend/tests/test_rs_*_seam.py` + try-import fallback in the Python adapter) to be the documented template, so that adding `boll.py` or `macd.py` next is a 1-day exercise, not 1-week.

## Implementation Decisions

### Module layout (Rust)

```
crates/indicators/src/
  lib.rs            # mod levels; m.add_function(wrap_pyfunction!(levels::support_resistance, m)?)
  sum.rs            # existing hello-world (kept; do not remove — seam test still exercises it)
  levels.rs         # NEW: support_resistance kernel
```

- `lib.rs` adds `mod levels;` and a second `m.add_function(wrap_pyfunction!(levels::support_resistance, m)?)?` — `sum_close` stays. The `__version__` registration is unchanged.
- `levels.rs` exposes exactly one `#[pyfunction] pub fn support_resistance(df: PyDataFrame, bins: u32) -> PyResult<PyDataFrame>` that takes the same `polars.DataFrame` the Python caller has and returns a `polars.DataFrame` with one new `chip_pct: f64` column (broadcast per row, as `sum_close` does in hello-world).

### Algorithm (Rust)

- 1:1 port of the current Python loop:
  - Pre-allocate `Vec<f64> chip` of length `bins`, initialised to 0.0
  - For each K-line (in input order, assumed sorted by `date` per Python's existing contract): `chip[i] = chip[i] * (1 - turnover_rate) + new_volume` for the price buckets in `[low, high]`
  - Append the **final** `chips` array of length `bins` to the returned DataFrame as a single-row `List<Float64>` column named `chip_pct`; Polars auto-broadcasts to match the input height (same pattern as `sum_close`'s scalar broadcast). The Python adapter then takes `to_list()[-1]` to recover the final chips and runs the existing reduce logic.
  - Inputs not satisfied (df.height < 20, no `volume`, no `turnover_rate`, `hi <= lo`) → return **same DataFrame** unchanged with a `chip_pct` column of `null`s (matches Python's "return []" + no-mutate contract)
- **Implementation choice for the bin-index math** (per research note `docs/research/levels-rust-api.md` §5): the inner loop is irreducibly a stateful Rust loop (each row's `chips` array update depends on the previous row). Hoisting the per-row bin-index math into Polars expressions or into `polars_ops::series::ops::cut` / `qcut` / `search_sorted` does **not** buy any vectorisation — `cut` returns categorical labels (not the integer indices the loop needs), `qcut` is quantile-based (wrong for uniform-spaced price bins), and `search_sorted` would just add an extra round-trip. **Approach A**: `Float64Chunked::to_vec()` once per column (`high`, `low`, `volume`, optional `turnover_rate`) — a single Arrow-buffer copy per column — then a single `for i in 0..n` Rust loop on `Vec<Option<f64>>` that does both bin-index and decay+distribute. No new `polars` feature flags required.
- Memory: `Vec<f64>(n × bins)` peaks at ~52 MB for 5,400 × 240 × 40. Acceptable; matches Python.

### Python wrapper (thin adapter)

```python
# backend/app/indicators/levels.py
def _support_resistance(df: pl.DataFrame, bins: int = 40) -> list[dict]:
    try:
        from tf_rs_indicators import support_resistance as _rs_support_resistance
    except ImportError:
        return _py_support_resistance(df, bins)        # pure-Python fallback

    out_df = _rs_support_resistance(df, bins)
    chip_col = out_df.get_column("chip_pct")
    if chip_col.null_count() == chip_col.len():
        return []                                       # kernel signalled no-op (all-null list)
    chip_lists = chip_col.to_list()                     # List<Float64> → list[list[float]]
    final_chips = list(chip_lists[-1])                  # broadcast target = the final chips array
    if len(final_chips) != bins:
        return []                                       # defensive
    edges = _bin_edges(df, bins)[3]                     # shared bin-policy helper
    close = float(df.tail(1)["close"][0])
    return _reduce_to_poc_and_dense(final_chips, edges, close)
```

- The pure-Python reference body (the `for row in range(n)` decay+distribute loop) is **renamed** to `_py_support_resistance` and is the fallback path. The reduce tail (POC + 2 dense zones) is **extracted** into the shared helper `_reduce_to_poc_and_dense(chips, edges, close)` so both the Python and Rust paths route through it. Bin policy (hi / lo / step / edges) is also extracted into the shared helper `_bin_edges(df, bins) → Optional[(hi, lo, step, edges)]`. Output is algorithmically identical to the original `_support_resistance`.
- The try-import + fallback matches ADR-0002 §5 (try-import default, `extras = ["rs"]` opt-in).

### Seams (where the test lives)

- **Rust unit (`crates/indicators/src/levels.rs::tests`)**: known-input → known-output vector of the **final 1-D `chip` array** (last row). No Python.
- **Python seam (`backend/tests/test_rs_levels_seam.py`)**: 4 tests in the style of `test_rs_indicators_seam.py`:
  1. parity: kernel output == `_py_support_resistance` output on a fixed 240-day fixture
  2. fallback: `tf_rs_indicators` import-disabled → still returns dicts (via `_py_support_resistance`)
  3. graceful no-op: empty df / df with no `volume` → returns `[]`
  4. dtype preservation: returned DataFrame has the same row count as input

The highest seam is "parity on a 240-day fixture" — bit-identical. This is the gate that holds the spec. If parity fails on the 240-day fixture, the spec is not done.

### Versioning & wheel

- `pyproject.toml` of the workspace root: no change. The wheel name (`tf_rs_indicators`), `pyo3-polars` features, and the `extras = ["rs"]` opt-in from ADR-0002 stay.
- `crates/indicators/Cargo.toml`: no new dependencies. The kernel uses only `polars::prelude::*` (for `Float64Chunked::to_vec` / `DataFrame` round-trip via `pyo3_polars::PyDataFrame`) — both already in the dependency set per ADR-0002. **No `cut` / `qcut` / `search_sorted` per the Ticket 01 research verdict.**
- Wheel: same `abi3-py310-win_amd64` matrix as the hello-world wheel. Desktop build picks up the change automatically.

### What we explicitly do NOT change

- Public function signature of `_support_resistance(df, bins=40) -> list[dict]`. The 7 callers in `app/api/levels.py`, `app/stock_analysis.py`, and the chart components stay untouched.
- `LEVEL_TYPES` dict, `PriceLevel` schema, the AI prompt template that consumes the dicts.
- `tiers.yaml`, `dev.ps1` / `dev.sh` desktop scripts.
- `Cargo.lock` (the kernel doesn't introduce new crate deps; only new internal modules).

## Testing Decisions

- **What makes a good test for this spec**: bit-identical output of the kernel and the Python reference, on a 240-day fixture that captures typical A-share turnover distribution. The fixture is committed under `backend/tests/fixtures/levels_240d.parquet` (or a small inline dict-of-lists, see step (a) below). Any divergence → spec fails.
- **Modules under test**: `crates/indicators/src/levels.rs` (Rust kernel) and the Python adapter path `app.indicators.levels._support_resistance` (integration).
- **Prior art for similar tests**:
  - `crates/indicators/src/sum.rs::tests` — Rust unit test, pattern follows.
  - `backend/tests/test_rs_indicators_seam.py` — 4-test dual-track pattern follows.
- **How the fixture is built** (one-time, then frozen):
  1. Capture the current Python `_support_resistance` output on a 240-day A-share fixture.
  2. Save the fixture (parquet) + the expected output JSON next to it.
  3. Both the Python reference and the Rust kernel are run against the fixture; the test compares outputs.
  4. If the test fails, the expected output is **NOT** updated — a failing test means the kernel drifted.

## Out of Scope

- Migrating other functions in `levels.py` (`_pivot`, `_extreme_levels`, `_bollinger`, `_keltner_*`, `_atr_stop`, `_gap`, `_fib`, `_round`) — they are pure Polars expressions or list-of-floats arithmetic, no Python loop. Polars 1.44 is already optimal.
- Migrating `pipeline.py::compute_indicators` — 100% Polars expressions, already vectorised. The `needed` graph resolution is orchestration, not compute.
- Changing the chart frontend (no UI change, no API change).
- Windows installer / Inno Setup pipeline (Tauri build picks up the new wheel automatically via the existing `pyo3-polars` discovery path).
- Profile / performance budget verification (the perf claim is "sub-second for 240-day × 5,400-stock refresh"; the bench harness to assert this is a follow-up spec, not this one).
- Switching the default fall-back policy. ADR-0002 §5 holds: try-import default, opt-in via `uv sync --extra rs`. This spec doesn't change it.

## Further Notes

- **Roll-out order**: this spec is the first business-logic migration after hello-world. It is **not** the last. The road to "fully Rust-enriched compute" is:
  1. Hello-world `sum_close` — done (this repo's hello-world, no production use).
  2. **`_support_resistance` — this spec**.
  3. `custom_signals_ai` DSL evaluate (per ADR-0001, second attack after indicators — `crates/factors` placeholder).
  4. BOLL / KDJ / MACD / RSI on GPU batch — `crates/signals` placeholder.
  5. AI-iterator over Polars expressions — `crates/indicators` extension.
- **Open question for the user (defer to implementation)**: should the try-import default switch to "Rust-first, Python fallback" once the wheel is signed off across a few weeks of production use? Per ADR-0002 §5 the default is currently Python-first. The spec preserves the default; flipping it is a separate, smaller decision.
- **Vendor patches interplay (TF-RS-1)**: the new kernel is pure-Rust loop on `Vec<Option<f64>>` from `to_vec()` + the PyDataFrame round-trip. None of the patched 5 sites (`unique.rs`, `lp.rs`, `functions.rs`, `row_deletions.rs`, `lower_ir.rs`) are touched by the `support_resistance` algorithm. The vendor patches stay required for the wheel to build, but the kernel is "downstream" of the patches and doesn't interact with them.
- **Per-machine reproducibility**: after this spec ships, `uv sync --extra rs && maturin develop --release` reproduces end-to-end on a fresh Windows box (Python 3.11+, Rust 1.98.1, Visual Studio Build Tools, `uv`, `maturin`). Per memory TF-RS-1 / winget pitfalls (non-elevated PowerShell, INK 5.1 quirks) all already worked through the hello-world PR.
